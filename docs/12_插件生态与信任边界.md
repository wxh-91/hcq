# 12 插件生态与信任边界

> 本文件覆盖 DSH 宿主/前端插件的拉取登记逻辑，以及网关到后端的外部访问鉴权与高危工具信任判定。后端 Python 动态插件见 [07_插件层与扩展契约.md]；高危工具清单与审计口径见 [06_权限与审计.md]；壳侧携带方式见 [11_多端生态与原生壳.md]。

## 1. 两套插件轨道

| 轨道 | 载体 | 入口契约 | 归属文档 |
|---|---|---|---|
| 后端 Python 插件 | 后端插件目录下含 `__init__.py` 子包 | 协议装饰器注册工具 | [07_插件层与扩展契约.md] |
| DSH 宿主/前端插件 | 注册表目录内 Node 包，host 入口 + 可选 `client.js` | 入口导出 `name`、`apply`，可选 `inject` | 本文件 |

## 2. 插件拉取与登记

### 2.1 管理端点

- `GET /v1/plugins`：列出注册表已登记插件，并对仍在注册表内的目录做一次实时兼容复核。
- `POST /v1/plugins/install`：按仓库地址拉取、校验、登记。
- `POST /v1/plugins/install-local`：登记本机已有目录，供兼容性实测与离线导入。
- 管理端点闸门：无身份返回 401，member 返回 403，admin 放行；身份以 8084 注入的 `X-User-Role` 为准，回环直连豁免为 admin。

### 2.2 来源白名单

- 仅接受 `github.com/<owner>/<repo>` 形态；兼容 `.git` 后缀、`tree/<branch>` 路径与 `github:owner/repo` 短链。
- 其余来源（非 GitHub 域名、空串）在解析阶段拒绝，返回 422。

### 2.3 下载与校验

- 下载：codeload 压缩包；分支顺序为传入分支 → `main` → `master`。
- 先解压到临时目录，静态校验通过后再落注册表；校验失败不入库，临时目录清理。
- 静态检查项：`package.json` 的 `name`、`version`；入口解析（`main`、`exports."."`、`lib/index.js`、`index.js`、`client.js`）；入口导出 `name` 与 `apply`（`inject` 可选）；`engines.dsh` 必填；`cordis.patch.yml` 存在记 bundle.patch 通过。
- 分级：无失败项且无警告为 `compatible`；有警告为 `compatible-warn`；任一失败项为 `incompatible`。

### 2.4 登记与挂载

- 清单：注册表 `registry.json` 记录名称、版本、来源、分支、入口、分级、检查项、警告、变更项与 `requires_restart`。
- profile 登记：Web profile `package.json` 写入 `link:` 依赖与 bundles 清单；`cordis.patch.yml` 追加插入项；登记幂等，已存在不重复写。
- 挂载：插件登记或升级后需重启 3080 工作台，由 DSH Loader 纳入启动清单；进程运行期不热加载。
- 顶层解析：宿主从顶层 `node_modules` 解析插件包；包名联接指向注册表目录缺失时，host 启动清单不收录该包 `client.js`。
- 前端形态：`client.js` 经组合 bundle 下发，向设置、模型分区、对话席等槽位注入 React 组件；原语槽位缺失处组件降级为空，不抛出未捕获异常。

## 3. 信任边界

### 3.1 判定优先级（高危工具）

`plugins/core_utils/trust.py` 按顺序判定，返回放行依据 `main_admin` / `role_admin` / `trusted_local` / `mobile_key`：

1. 主管理员标识（`DEFAULT_ADMIN`）→ 放行；
2. 请求上下文 `role=member` → 拒绝；
3. 请求上下文 `role=admin` → 放行；
4. 可信本地来源：回环地址（`127.0.0.1`、`::1`、`localhost`、`127.*`）或 `.env` 的 `TRUSTED_LOCAL_HOSTS` 逗号显式列出的地址 → 放行；
5. 其余非可信来源：携带与 `MOBILE_API_KEY` 恒定时间比对一致的专属 Key → 放行；期望 Key 为空时失败关闭；
6. 其余一律拒绝。

- 会话前缀只用于记忆分桶，不赋予任何高危权限。
- 判定只作用于高危工具，不改变模型选择与工具可见性。

### 3.2 网关身份识别

- 8083 `gateway.py` 身份取自 8084 注入的 `X-Auth-Source` / `X-User-Id` / `X-User-Role` 头；无头且回环直连豁免为 `local-admin` / admin；其余为匿名。
- 8083 以 `--no-proxy-headers` 启动，`request.client` 取真实 socket peer，不随 `X-Forwarded-For` 改写；来自 8084 的转发因此显示为回环来源并接受注入身份，非回环直连即使自带身份头也判匿名。
- 聊天端点缺少角色头返回 401；管理端点无身份 401、member 403、admin 放行。
- 网关层不做自然语言与正文正则拦截；高危角色闸门下沉到后端 AUP 执行层，按上下文角色精确判定。
- 可信本地额外地址仅来自 `TRUSTED_LOCAL_HOSTS`；经端口代理转发、源地址被改写的网关地址不自动视为机主。

### 3.3 身份透传现状（边界记录）

- 8084 反向代理剥离逐跳头与客户端可伪造的身份头，由本网关注入可信的 `X-User-Id` / `X-User-Role` / `X-Auth-Source`，转发 127.0.0.1:8083。
- 后端 `request.client.host` 恒为网关到后端的回环地址；原始外部 peer 地址经 `X-Forwarded-For` 续接，不进入高危角色判定。
- 角色随请求负载 `user_role` / `user_ref` 进入后端请求上下文；后端高危判定以角色优先，未带角色时回退可信本地与专属 Key 判定。

### 3.4 公网来源闸门

- 8084 判定 `public_edge`：`X-Forwarded-For` 末跳不属于私网前缀（`10.`、`127.`、`172.16.`～`172.31.`、`192.168.`、`::1`）即为公网来源。
- `public_edge` 为真时，回环豁免（`loopback_exempt`）与内部令牌豁免（`internal_token`，头名 `x-hcq-internal`）一律失效，只接受 `Authorization: Bearer` JWT；两者同时携带按匿名处理并返回 401。
- 内部令牌随 APK 分发，等于局域网机主凭据；它只在回环与局域网来源有效，不得作为公网通行凭据。
- 复核命令：公网携带内部令牌访问 `/v1/models` 期望 401，本机 `127.0.0.1:8084` 与局域网 `:8084` 携带同一令牌期望 200。

## 4. 当前观测坐标

- 角色闸门：member 调用高危工具被 AUP 层拒绝并落 `audit.log` denied 记录；admin 放行并落 success 记录；审计坐标见 [10_生产坐标红线与运维规程.md]。
- 已登记前端插件：`dsh-cookie-cleaner` v0.1.7、`dsh-mo-image` v0.5.1，分级 `compatible`；`dsh-mo-image` 在工作台对话席渲染生图模型席位。
- 插件清单实时复核走 `GET /v1/plugins`；安装与登记的兼容结论只落注册表 `registry.json`，不另存截图或导出文件。

## 5. 何时查本文档

- 插件安装被拒、分级不符、重启后前端未出现。
- 局域网/外部访问被 401、403 拦截，或注入身份头缺失。
- 高危工具放行依据与预期不符；需要判断放行来自主管理员、admin 角色、可信本地还是专属 Key。
- 引入外部访问入口或调整可信本地地址前，先复核第 3 节顺序与透传边界。
